# 战斗声明中心

## 职责与边界

`BattleEventHub` 统一声明种类、事件身份、不可变结果快照和订阅入口。业务脚本仍负责计算与提交结果；响应继续进入 `BattleResolutionContext` / `BattleExecution`，没有新增第二条队列。

不提供“全局最近一次事件”，不保留整场历史。事件由具体发生对象、当前响应和待执行请求持有；发生对象的查找使用弱引用关联。一次发生对象只能发布一次，战斗重置后旧声明不能再次发布。

这次兼容了独立状态实例容器、DMGTaken 快照，以及伤害脚本新增的原始附着量、夜魂伤害标记、LogicalHitID。保留现有 TeamBonuses 的订阅与规则，不在声明中心重新实现一套队伍效果。

## 身份

| 字段 | 含义 |
| --- | --- |
| SessionId | 战斗会话代次，重置后不同 |
| EventId | 本次事实唯一编号，不是配表 ID |
| ResolutionId | 当前根结算链编号 |
| ActionExecutionId | 一次真实主动技能行动的执行身份；起止及本次全部hit共享，嵌套行动使用新编号，非主动技能容器为0 |
| ActionScopeId / EffectScopeId | 行动、效果次数额度作用域的身份；独立状态的本次阶段调用及全部延伸也共用ActionScopeId |
| EffectExecutionId | 一次效果执行身份；RepeatEffect 的重复执行继续共享原执行编号 |
| HitId | 一次逻辑 hit；同 hit 的群体目标、溅射共享，派生命中使用自己的批次身份 |
| TargetIndex | hit 内的目标顺序，从 1 开始；没有可靠顺序时为 0 |
| CauseEventIds | 直接因果事件编号，可有多个，不把多来源传播强行归并成一个来源 |

没有对应语义的字段为 0，例如行动开始尚未进入某个 hit。历史兼容入口没有提供执行信息时也不能凭配表 ID 猜造运行时编号。结果里的实体引用用于定位实时对象，事件数值、来源 ID、前后余额等独立快照，不随之后的事件改变。

独立状态行动由BattleResolutionContext.BeginIndependentStatusAction包住具体状态本阶段本次调用的全部行动行、效果与延伸响应；已有外层行动时沿用，下一次阶段触发才建立新范围。CurrentAction.IndependentStatus可查询独立根状态。这里只补Action限次范围，不额外提交主动行为起止声明；独立执行时ActionExecutionId仍为0，不以状态伤害冒充角色或敌人技能行动。

`ActionExecutionId`由实际技能执行入口建立、随声明和待执行请求保留，退出作用域后恢复调用者。它与可能被嵌套响应共享的`ActionScopeId`限次额度不是同一概念，不据此重置原有限次。敌方暂统一`EnemySkill`，一份完整Skill序列开始、完成各声明一次；多hit/多目标/溅射不拆成新行动。未选到技能、行动前被限制、执行取消/异常或战斗结束不伪造完成。琴的领域反击及六命扣次在完整行动结束后消费本次实际命中事实，不需要新增攻击行动分类；详细调用要求见`codex_files/战斗声明提交规则.md`。

## 已接入的事实与时点

| 声明 | 发布边界 |
| --- | --- |
| ActionStarted / ActionCompleted | 我方 ActiveActionQuery 认定的主动行动开始与成功完成；敌人技能序列开始、完成。取消、异常不伪造完成 |
| DamageResolved | HitBatch 全部目标提交 HP 后收集；保留护盾前伤害、吸收量、实际扣血、命中、元素、原始附着量、夜魂伤害标记 |
| HPChanged | 已提交伤害扣血、非伤害 HP 消耗、治疗实际回血；不把伤害预计值当生命变化 |
| HealResolved | 预计算时捕获原有候选，整段 HP 和生命之契提交完毕后发布；包含实际治疗、溢出与抵扣 |
| ReactionOccurred | 具体 ReactionOccurrence 对应一次声明；重复调用旧通知不重复发布 |
| ResourceChanged | 夜魂、生命之契、能量入口提交后，保留请求变化和实际前后余额 |
| APSpent | 已消耗的 AP，保留 amount；有全局 AP 池时附带前后余额，独立通知没有池时余额为空 |
| SwitchResolved | 换人实际完成后，保留进出场双方 |
| StatusAdded / StatusRemoved | 正式状态进入、离开容器时；绑定和 OnApply/清理完成后才执行收集的响应 |
| ShieldChanged | 护盾增加、覆盖、吸收、敌方元素盾损失、移除、到期和绑定时长刷新后的池快照 |
| Death | 保持在本层普通响应之后；死亡响应及其子链结清后才检查战斗结束 |

普通状态以具体实例及 ApplyOrder 标识，不按同 ID 合并监听者。满额替换、到期分别标记 Replaced、Expired；其他未细分的移除统一标记 Removed，不猜测原因。原型状态、战斗初始化赋值、重置清场不等同于战斗内的施加/资源获取。

## 资源

`ResourceChangeReason` 明确区分：

- Gain：增加。
- Spend：主动消耗。
- Decay：自然衰减，角色自己的自动扣减应显式传入此原因。
- Clear：清空或载体移除，不是主动消耗。
- HealingAbsorption：生命之契抵扣治疗，不是主动消耗。
- Adjustment：其他明确的规则调整。

夜魂存储和增减仍为 int，生命之契仍为 float；公共声明用 double 传输，避免大 int 被 float 损失精度。资源声明保存发生时的 WasOnField，不应通过响应执行时是否在场倒推过去。

非零请求即使被上限/下限截断，也保留请求和实际余额；Removed/Added 只算实际变化。因此从 0 请求消耗、满值请求获取都不能用请求量冒充实际量，角色溢出规则可以读取两者差额。

```csharp
// 主动消耗，实际最多扣到 0。
NightSoulStatusHandler.ReduceValue(owner, 5);
// 自然扣减，不会触发 NightSoulConsumed。
NightSoulStatusHandler.ReduceValue(owner, 1, ResourceChangeReason.Decay);
// 清空不会冒充 Spend。
NightSoulStatusHandler.ClearValue(owner);
```

## 元素三类事实

1. `ElementContactResolved`：一次有正元素量的元素交互结果，包含请求量、剩余量、来源和反应类型。接触不保证留下普通附着，风岩不因此产生普通元素池。
2. `ReactionOccurred`：反应确实发生。由 handler/Resolver 的 ReactionOccurrence 给出，不从池前后差额猜反应。
3. `AuraChanged`：一个真实写回事务的最终元素池变化，分别快照普通附着、冻结虚拟冰、燃烧虚拟火，以及来源、原点阶段、刷新标记。

`ElementEventScope` 包住一次反应的准备、消耗和写回。同元素覆盖中的临时 RemoveAura + ApplyAura 不分别广播“先失去再获得”。数值不变但明确重施的保留池可以声明刷新；已经被完全反应掉的中间池不声明刷新。

扩散保留原有边界：第一阶段伤害及源池消耗 → 第二阶段相邻传播批量写回 → 反应附带效果 → 第三阶段残留清算。各阶段可以各自产生元素池事实，不包住整个扩散只发一次净差额。合并传播记录全部输入事件编号，原来的伤害归功规则不变。

## 响应顺序与接口

`Record` 创建结果并捕获当时的订阅者/状态实例；它不表示已经广播。批次可以先记录，待提交完再 `Dispatch`。`Publish` 是已提交事实的 Record + Dispatch。不得为未实施的效果构造一份看似成功的声明。

所有候选继续按全局 ApplyOrder、同序号下的提交顺序排序，再确认状态条件与次数额度。概率只在原确认阶段抽一次；执行时只复查实例仍在宿主上/订阅仍有效，不重复抽概率。子响应深度优先结清，再执行已经预占的下一个同层响应。类型订阅也进入相同的链深度保护。

```csharp
IDisposable subscription = BattleEventHub.Subscribe<ResourceEventData>(
    BattleEventKind.ResourceChanged,
    (header, change) =>
    {
        if (change.Subject != owner || change.Resource != "NightSoul"
            || change.Reason != ResourceChangeReason.Spend || change.Removed <= 0) return;
        // 读取这个声明自己的变化量；执行本规则已有的接口。
    },
    applyOrder: status.ApplyOrder,
    isActive: () => status.IsActive && owner.HasStatusInstance(status));
// 生命周期结束时取消订阅。isActive 只作有效性检查，不放概率或业务副作用。
subscription.Dispose();
```

响应脚本从 `ScriptHookContext.Current.Declaration` 或当前调用链的 `BattleEventHub.Current` 获取自己的声明。异步排队会保存上下文；子事件结束后恢复父事件，不覆盖其他待执行请求。

新声明驱动的配表钩子包括 ResourceChanged、NightSoulConsumed、AuraChanged、ElementContactResolved；参数可为 Self、Equipper、角色数字 ID 或 All。NightSoulConsumed 只接受实际主动扣除大于 0 的夜魂声明。现有 NightSoulBurst 钩子及 TeamBonuses 发布者原样保留。原 OnHit、OnDamage、治疗、APUsed、ReactionTriggered、Switch、Kill 仍由兼容适配入口提供原有筛选，不再重复执行一次。

只有列出的钩子实现了配表解析；其他声明可通过类型订阅使用，不能仅因枚举存在就在 ScriptHook 里任意填同名函数。本次没有新增技能 EffectType。

## 接入约束

- 战斗内修改数值、状态、护盾、附着必须经过相应业务入口。直接改公开字段、直接增删容器不会自动被中心侦测，也不轮询补造声明。
- APSpent 对应现有的消耗通知，不把回合重置 AP 自动包装成消耗事件。
- 不把持续反应创建时的来源归功快照误作这一次回合 tick 的事件身份；来源和发生次数是两回事。
- 源数据读取路径不变，本次没有检查或修改 StreamingAssets、配表同步和套装配置。

## 人工回归清单（未执行）

1. 群体伤害及溅射：同 hit 相同 HitId、独立目标序号；不同 hit 不同编号。DMGTaken、暴击、护盾计算保持原规则。
2. 完全被盾吸收：命中仍可成立，实际 HP 伤害为 0；护盾池变化不是 HPChanged。
3. 群体治疗同时抵扣生命之契：所有目标提交后才确认条件，抵扣原因是 HealingAbsorption，不触发主动消耗规则；只有实际回血才发 HPChanged。
4. 夜魂从 3 请求消耗 5：实际消耗 3；从 0 再请求消耗、自然衰减、清空均不触发 NightSoulConsumed。获取超过上限时请求量和实际获取量不同。
5. 同 ID 多实例：一次到期或替换只移除对应实例，其他实例仍可响应；记录之后新增的实例不能追溯旧事件，被移除后重建的同 ID 实例不能接替旧请求。
6. 同元素覆盖：没有中间丢失/获得通知；冻结、燃烧与普通冰火分池。元素自然衰减如实声明前后池。
7. 多源扩散：源池消耗与传播写回有各自快照，传播保留全部因果编号，残留清算不提前；伤害归功仍按旧规则。
8. 多个状态、队伍效果响应同层事件：全局 ApplyOrder 排序，条件概率不重抽，子链深度优先，次数先预占；记录后新订阅者不能补领旧声明。
9. 嵌套反应/治疗/换人后，父响应仍能读到自己的 Declaration，WasOnField 不被后来的换人改变。
10. 击杀最后一个敌人：普通响应先于死亡响应，最后再检查胜负；重复通知同一反应不重复广播。
11. 异步表现等待、取消和重开：旧会话订阅被释放，旧声明不在新战斗重新发布。
